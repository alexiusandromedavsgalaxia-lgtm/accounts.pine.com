Overview

Pine Accounts is a React + Vite account portal deployed on Cloudflare Pages. It provides a Pine Account identity, persistent browser sessions, a Developer Account area and authenticated access to account data.

Site navigation

Signed-out state

The header shows the Pine identity and two actions: Sign in and Create Account. The main card switches between authentication forms without leaving the page.

Signed-in state

The header changes to an Account/Developer switch. Account is the default authenticated view. Developer loads its data from /api/developer.

Account screen

  • Displays the user's name and email.
  • Account details expands the account information panel.
  • Developer Account opens the developer area.
  • Sign out destroys the current session server-side and clears the cookie.

Developer screen

The Developer screen has four sections: Account, Projects, Credentials and Services. Account is the fully populated section in the current implementation.

Authentication

Authentication is handled by /api/auth/*. Passwords are never stored as plaintext. A per-user random salt is stored with the user record and the password is derived with PBKDF2 using SHA-256 and 100,000 iterations.

POST/api/auth/registerpublic

Creates a Pine Account and starts a 30-day session.

{
  "name": "Alex",
  "email": "alex@example.com",
  "password": "at-least-8-characters"
}

Success returns 201, a public user object and an HttpOnly pine_session cookie.

POST/api/auth/loginpublic

Checks the supplied email and password and starts a new 30-day session.

{
  "email": "alex@example.com",
  "password": "your-password"
}
GET/api/auth/mesession

Returns the current user when a valid session exists. With no session, user is null.

{ "user": { "id": "...", "name": "...", "email": "..." } }
POST/api/auth/logoutsession

Deletes the current session record and expires the cookie.

{ "ok": true }

Developer Account

A Developer Account is a separate record linked one-to-one with the Pine Account through user_id. Creating it generates a Pine API key and defaults the plan to free and status to active.

GET /api/developer

Returns the developer record belonging to the authenticated Pine Account, or null when it does not exist.

POST /api/developer

Creates the developer record if one does not already exist. Repeating the request returns the existing record rather than creating a second one.

The UI intentionally shows all 13 columns. Projects, Credentials and Services are currently presentation areas for future functionality.

Account Data API

The unified endpoint is https://accounts.pine.com/api/data. Every request must specify one of three scopes: account, developer or data. Authentication is based on the current pine_session cookie, so data is always resolved for the signed-in user.

Three scopes, one endpoint.?scope=account targets the Pine Account, ?scope=developer targets the Developer Account, and ?scope=data targets arbitrary user-owned key/value data.

GET /api/data?scope=account

Reads the authenticated user's id, name, email and created_at.

PUT or POST /api/data?scope=account

Updates name and/or email.

{
  "name": "New name",
  "email": "new@example.com"
}

GET /api/data?scope=developer

Reads all 13 current developer_accounts columns for the signed-in owner.

PUT or POST /api/data?scope=developer

Updates only name, email, company, website and description. Identity, plan, status and API-key fields are not writable through this endpoint.

{
  "company": "Pine Labs",
  "website": "https://example.com",
  "description": "A Pine developer."
}

GET /api/data?scope=data

Returns every key/value record owned by the authenticated user, ordered by key.

POST or PUT /api/data?scope=data

Creates or replaces one user-owned key/value entry. A repeated key updates the existing record because user_id + key is unique.

{
  "key": "theme",
  "value": "dark"
}

value can be a string, object, array, number, boolean or null. Non-string values are serialized to JSON.

API authentication

Protected endpoints look for the pine_session cookie. The raw session token is not compared directly with the database. The server derives a hash of the token with PBKDF2 and looks up the resulting token_hash in the sessions table, also checking that expires_at is still in the future.

The session cookie is configured as HttpOnly, Secure and SameSite=Lax, with a 30-day lifetime.

Important:Calling protected endpoints manually requires an authenticated browser/session context. The public URL alone does not grant access.

Frontend architecture

src/App.jsx contains the main React application and defines the Pine logo, input field, authentication view, account view and Developer view.

  • Auth owns registration/login form state and calls the auth API.
  • Account owns the signed-in account screen and logout action.
  • Developer loads and creates the Developer Account and controls its four sections.
  • App checks /api/auth/me on startup and decides which view to render.

src/styles.css supplies the visual system, responsive developer data layout, loading states and page-entry animation.

Security model

  • Password material is derived with PBKDF2 rather than stored directly.
  • Each user has a separate password salt.
  • Session tokens are random and only their derived hashes are stored.
  • The session cookie is HttpOnly and Secure.
  • Protected queries scope records to the authenticated user's ID.
  • Developer updates use an explicit allow-list rather than accepting arbitrary column names.
  • Protected data responses are marked Cache-Control: no-store.

The current API is an application-level account API, not a generic SQL interface. Clients cannot submit arbitrary SQL or request another user's records through these endpoints.

Deployment

The project is configured for Cloudflare Pages with Vite output in ./dist. Wrangler declares three D1 bindings.

pages_build_output_dir = "./dist"

[[d1_databases]]
binding = "accounts"
database_name = "accounts"

[[d1_databases]]
binding = "developeraccounts"
database_name = "developer-accounts"

[[d1_databases]]
binding = "dataacc"
database_name = "account-data"

Cloudflare Pages supplies these D1 bindings to Functions through c.env.
