Overview

Pine Accounts is the identity and account layer behind Pine services. The application provides account creation and sign-in, persistent sessions, a personal account surface, an optional Developer Account and authenticated storage for account-owned data.

IdentityUsers, names and unique email addresses.
AuthenticationPBKDF2 password derivation and session cookies.
DeveloperOne Developer Account per Pine Account.
DataScoped account and key/value data APIs.
RuntimeCloudflare Pages Functions.
StorageThree Cloudflare D1 bindings.
Documentation principleThis reference describes the implementation currently exposed by the repository. It is not a promise that every future Pine service will use the same endpoints or schema.

Quickstart

The simplest integration is to let Pine Accounts manage the browser session and call authenticated endpoints from the same origin.

1. Create an account

POST /api/auth/register
Content-Type: application/json

{
  "name": "Alex",
  "email": "alex@example.com",
  "password": "at-least-8-characters"
}

2. Resolve the current session

GET /api/auth/me

3. Read account data

GET /api/data?scope=account

4. Store synchronized user data

POST /api/data?scope=data
Content-Type: application/json

{
  "key": "theme",
  "value": "dark"
}
Browser sessionsRequests made by the signed-in browser automatically include the Pine session cookie for same-origin calls. Do not expose the session token to client-side application storage.

Core concepts

Pine Account

The Pine Account is the primary identity. Its stable id is used to associate sessions, Developer Account records and user-owned data.

Developer Account

A Developer Account is an optional one-to-one extension of the Pine identity. It carries developer metadata, plan/status information and a generated API key.

Scopes

The Account Data endpoint uses an explicit scope query parameter. The current values are account, developer and data. A missing or unknown scope is rejected.

Ownership

Protected records are selected using the authenticated user's ID. The client does not supply another user's ID to read someone else's account through these endpoints.

Authentication

Authentication is implemented in functions/api/auth/[[route]].js. Registration validates the submitted identity, creates a random user ID and password salt, derives a password hash with PBKDF2-SHA-256 using 100,000 iterations, stores the user and creates a session.

POST/api/auth/registerpublic

Creates a new Pine Account and immediately starts a 30-day session.

{
  "name": "Alex",
  "email": "alex@example.com",
  "password": "at-least-8-characters"
}

201 Created

{
  "user": {
    "id": "uuid",
    "name": "Alex",
    "email": "alex@example.com"
  }
}
POST/api/auth/loginpublic

Looks up the email, derives the supplied password with the user's stored salt and compares the result with the stored hash. On success a fresh 30-day session is created.

{
  "email": "alex@example.com",
  "password": "your-password"
}
GET/api/auth/mesession

Resolves the active browser session. Expired or missing sessions produce user: null.

{ "user": null }
POST/api/auth/logoutsession

Hashes the current session token, deletes the matching database row and expires the browser cookie.

Sessions & cookies

The browser receives a cookie named pine_session. The raw token is random data generated with the Web Crypto API. The database stores a PBKDF2-derived representation rather than the raw token.

PropertyCurrent behavior
Cookiepine_session

SecureEnabled, requiring HTTPS.

Do not copy session cookiesA session cookie is an authentication credential. Integrations should use the supported authenticated browser flow rather than exposing or transporting it manually.

Updating identity

PUT or POST /api/data?scope=account can update the name and email for the authenticated account. Email addresses are normalized to lowercase and checked against existing users.

{
  "name": "New name",
  "email": "new@example.com"
}

Developer Account

The Developer Account is stored in the developer_accounts table of the developer-accounts database. Each Pine Account can have at most one record because user_id is unique.

GET /api/developer

Returns the authenticated user's Developer Account, or null if none exists.

POST /api/developer

Creates the Developer Account. Creation generates an ID, API key and timestamps. If a record already exists, the endpoint returns it instead of creating a duplicate.

Editable fields

The Account Data API permits updating name, email, company, website and description. Plan, status and API-key fields are not writable through that endpoint.

Account Data

The account-data D1 database provides the generic account_data table for user-owned key/value records. This is the storage layer used for data that belongs to an account but does not need a dedicated schema field.

ColumnMeaning
idUnique record UUID.
user_idOwning Pine Account.
keyUser-defined data key.
valueString or serialized JSON value.
created_atRecord creation timestamp.
updated_atLast replacement timestamp.

The pair user_id + key is unique. Writing an existing key therefore replaces its value rather than creating duplicate rows.

JSON values

{
  "key": "preferences",
  "value": {
    "theme": "dark",
    "language": "es"
  }
}

Non-string values are serialized as JSON before storage. Reads return the stored representation.

Database model

Pine Accounts currently uses three D1 bindings so identity, developer records and generic account data remain separate.

BindingDatabaseTablesRole
accountsaccountsusers, sessionsIdentity and authentication.
developeraccountsdeveloper-accountsdeveloper_accountsDeveloper identity and credentials.
dataaccaccount-dataaccount_dataUser-owned synchronized data.

Relationships

users.id is the ownership key. A session references a user ID, a Developer Account references the same user ID, and account-data rows carry the same user ID. This gives the application one consistent identity boundary.

Security

  • Passwords are never stored as plaintext.
  • Each account has its own password salt.
  • Password derivation uses PBKDF2 with SHA-256 and 100,000 iterations.
  • Session tokens are generated with Web Crypto and only a derived representation is stored.
  • Session cookies use HttpOnly, Secure and SameSite=Lax.
  • Protected records are scoped to the authenticated user.
  • Developer updates use an explicit field allow-list.
  • Data API responses use Cache-Control: no-store.
Security boundaryThe public API is not a raw D1 interface. Clients cannot submit SQL through these routes or choose an arbitrary user's records.

Frontend architecture

The main application lives in src/App.jsx and uses a small client-side state model to switch between signed-out authentication, Account and Developer views.

Authentication view

The form sends JSON to /api/auth/register or /api/auth/login. On success the returned user object is stored in React state.

Account view

The account dashboard renders identity information, account actions, Developer Account access and service links. Logout calls the server endpoint before returning to the signed-out state.

Developer view

The Developer screen requests /api/developer and can create a record through the same endpoint. The account panel exposes the full 13-column record.

Theme synchronization

The main Pine interface stores the selected appearance in localStorage under pine-theme. This documentation page reads the same value before rendering, so its appearance follows the user's selected light/dark preference.

Runtime boundaries

The React bundle runs in the browser. API functions run on Cloudflare's server-side runtime. D1 access is performed by those functions through the configured environment bindings.

Troubleshooting

Login or registration returns an error

Check that the request reaches /api/auth/login or /api/auth/register, uses JSON and contains the required fields. A duplicate email returns 409; an invalid login returns 401.

/api/auth/me returns no user

The browser may not have a valid pine_session, or the session may have expired. Sign in again rather than attempting to copy the cookie manually.

Developer Account is null

A Pine Account can exist without a Developer Account. Create one through the Developer view or POST /api/developer.

Data scope is rejected

Use exactly account, developer or data in the scope query parameter.

D1 authorization errors

Verify that the Cloudflare Pages project has the three expected D1 bindings and that their binding names match the names used by the Functions.

Advanced implementation reference

Request lifecycle

Every protected request begins by resolving the pine_session cookie, deriving its server-side representation and locating an unexpired session. The session is joined to the owning user before any account, developer or data query is executed. This keeps authorization tied to the authenticated identity rather than to an arbitrary ID supplied by the browser.

Ownership model

The same user identifier is the common ownership key across identity, developer and generic data storage. A Developer Account uses a unique user_id, while generic data uses user_id + key as its uniqueness boundary. This means the API can safely scope reads and writes to the session owner.

Idempotency

Developer Account creation is intentionally idempotent for an existing user. Generic data writes are also naturally repeatable for the same key because an existing row is updated instead of duplicated. Authentication is different: successful registration and login create new sessions.

Serialization

Generic Account Data accepts strings directly. Objects, arrays, numbers, booleans and other JSON-compatible values are serialized before storage. Consumers should therefore treat the returned value as the stored representation and parse JSON when they know the key contains structured data.

Limits and defensive boundaries

Names, developer metadata, descriptions and keys have explicit length limits. Unknown scopes and unsupported HTTP methods are rejected. Developer writes use an allow-list instead of accepting arbitrary column names. These constraints prevent the generic endpoint from becoming an unrestricted database editor.

Static documentation

The documentation is served as a static page from the public site, while API handlers execute through Pages Functions. The documentation itself does not receive database credentials and should never be treated as an administrative database console.

Handling authentication failures

A client should treat 401 as a signal that it needs a valid session. The recommended browser behavior is to return to the sign-in surface rather than storing a copy of a session token or attempting to manufacture one.

Security model and operational guidance

Pine separates browser presentation from server-side authorization. The React application can request an endpoint, but it does not decide which user owns a record. That decision is made from the authenticated session on the server.

  • Never put D1 binding names, secrets or server credentials into client JavaScript.
  • Never commit a Developer API key to a repository.
  • Never use the generic data endpoint as a SQL execution mechanism.
  • Do not rely on the user-supplied user_id as an authorization decision.
  • Use HTTPS in every deployed environment.
  • Invalidate sessions through the supported logout flow.
  • Review API changes together with database changes.
Production noteThe current implementation is a compact account platform. Features such as password reset, email verification, MFA, API-key rotation and fine-grained developer permissions require dedicated implementations before being represented as production security guarantees.

Platform roadmap boundaries

The following concepts may appear in the product interface or surrounding Pine projects, but they are not automatically part of the current API contract: project management, service publishing, credential rotation, binary photo storage, MFA, password recovery, email verification, audit logs and organization/team accounts.

When any of these become implemented, their endpoints, schemas, authorization rules, lifecycle states and migration strategy should be documented here rather than inferred from a visual placeholder.

Architecture in depth

Pine Accounts is divided into a browser application, Pages Functions and three D1 databases. The browser is responsible for presentation and user interaction. The server-side Functions are the authorization boundary. D1 stores identity, developer metadata and generic account-owned data in separate logical databases.

Request lifecycle

  1. The browser sends a request to a Pages Function.
  2. The Function reads the pine_session cookie when authentication is required.
  3. The session token is derived with the session-specific PBKDF2 configuration.
  4. The derived value is compared against the session table and its expiration.
  5. The authenticated user ID becomes the ownership boundary for subsequent queries.
  6. The Function executes a parameterized D1 query and returns JSON.

Database separation

The accounts binding owns primary identity and sessions. developeraccounts owns the one-to-one developer extension. dataacc owns generic account data. This separation makes the ownership model explicit and keeps the generic data store from becoming the identity database.

Request and response conventions

JSON APIs use JSON request bodies and JSON responses. Successful protected data responses are marked Cache-Control: no-store. Clients should treat unknown response fields as forward-compatible additions rather than depending on object key order.

Content type

For JSON writes, send Content-Type: application/json. A malformed body is rejected rather than interpreted as form data.

Ownership rule

Protected endpoints derive ownership from the session. A client should never attempt to impersonate another account by changing a user_id field in a request body.

Integration patterns

Browser integration

const response = await fetch("/api/data?scope=data");
const result = await response.json();

For same-origin browser integrations, the browser can manage the Pine cookie automatically. Applications should not copy the session token into localStorage.

Reading a preference

const result = await fetch("/api/data?scope=data").then(r => r.json());
const theme = result.data?.find(item => item.key === "theme");

Writing structured data

await fetch("/api/data?scope=data", {
  method: "POST",
  headers: {"Content-Type": "application/json"},
  body: JSON.stringify({
    key: "preferences",
    value: {theme: "dark", language: "es"}
  })
});

Idempotent key writes

Because user_id + key is unique, writing the same key repeatedly updates the existing record. This makes preference synchronization naturally idempotent when the latest value should win.

Account scope

The account scope exposes only the identity fields intended for the account surface. Password hashes, salts and session tokens are not returned by the public account-data response.

Developer scope

The developer scope returns the complete developer record because it is an administrative surface for the authenticated owner. The API key remains a credential and should not be copied into public client code.

Data scope

The data scope lists records ordered by key. Each record includes its ID, key, stored value and timestamps.

Schema reference

users

Primary identity table. The email is unique. The password representation is salted and derived.

sessions

Session table containing a derived token, owning user ID and expiration timestamp. The active-session query requires the expiration to be later than the current database time.

developer_accounts

The developer table has thirteen fields and a unique user_id. Creation timestamps and update timestamps are stored independently so consumers can distinguish record creation from later metadata changes.

account_data

Generic account storage with a uniqueness constraint over user_id,key. Values are text at the D1 layer, with non-string JavaScript values serialized to JSON before storage.

Security model

Password handling

The application never needs to retrieve the original password from D1. Registration creates a salt and stores only the derived value. Login repeats the derivation using the stored salt.

Session handling

The raw browser token is carried by an HttpOnly Secure cookie. Server code derives it before database lookup. Logout removes the corresponding session record and expires the cookie.

SQL safety

Dynamic user values are passed through parameter bindings rather than concatenated into SQL statements. The developer update path restricts writable column names to an explicit allowlist.

Cache safety

Authenticated data responses use no-store. This is important for account information because a cached authenticated response could otherwise outlive the request context.

Client-side boundaries

Theme preference is intentionally local UI state. It is not used as an authentication mechanism and must never be treated as proof of account ownership.

  1. Build the Vite application.
  2. Publish the generated dist directory.
  3. Deploy the functions directory as Pages Functions.
  4. Verify every D1 binding exists in the Pages project.
  5. Verify the production hostname uses HTTPS.
  6. Test registration, login, /me, logout and protected data routes.

Testing checklist

  • Create a fresh test account with a unique email.
  • Confirm registration returns a user and establishes a session.
  • Reload the page and verify /api/auth/me resolves the session.
  • Sign out and verify protected routes return 401.
  • Sign back in from another browser/device and verify the same account identity is resolved.
  • Create a Developer Account and verify the one-to-one constraint.
  • Write a data key, read it back, update it and verify the same key is replaced.
  • Try an invalid scope and confirm HTTP 400.
  • Try another account's ID in a client payload and verify it does not change ownership.

Compatibility and evolution

Clients should depend on documented paths and fields rather than internal implementation details. New fields may be added to responses. A client should ignore fields it does not understand.

API keys, session cookies and database identifiers have different purposes. A database ID is not automatically an authorization credential. A session token is not an API key. An API key should not be treated as a substitute for a browser session unless a future API explicitly documents that behavior.
